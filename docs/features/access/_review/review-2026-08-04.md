## Findings

### F1 — Stage 1: mutation-only users are locked out of required workflows

- Evidence: `apps/web/src/modules/access/page.tsx:19` renders the unavailable state unless the caller has `ROLES:WATCH` or `USERS:WATCH`, even when the projection contains an independent mutation Permission.
- Contract: AC-03, AC-06, AC-08, AC-11, AC-13, AC-15, and AC-19 grant create, update, assignment, deletion, and transfer capabilities independently; the web must not hide a capability the caller holds.
- Required change: admit all supported access capabilities and render only the datasets and actions authorized by the projection, without weakening server enforcement.
- Disposition: unresolved; fix required before ship.

### F2 — Stage 1: assigned-Role deletion breaks without member-read authority

- Evidence: `apps/web/src/modules/access/components/access-workspace/AccessWorkspace.tsx:163` passes `[]` when the caller cannot read members; `apps/web/src/modules/access/components/access-administration/AccessAdministration.tsx:406` derives whether replacement is required from that list and submits `null` at `:421` when it appears unassigned.
- Contract: AC-11 and AC-12 require assigned-Role replacement and atomic rollback. A caller with `ROLES:DELETE` must not need unauthorized `USERS:WATCH` data to complete the server-authorized workflow.
- Required change: expose deletion-safe assignment metadata through a Role-authorized contract or use a server-driven prepare/delete flow that does not disclose member data.
- Disposition: unresolved; fix required before ship.

### F3 — Stage 1: mutation failures and concurrent revocation are not exercised through the real workflow

- Evidence: `apps/web/src/modules/access/components/access-administration/AccessAdministration.spec.tsx:56` supplies only successful callback doubles; `apps/web/src/modules/access/components/access-administration/AccessAdministration.spec.tsx:179` proves controls are absent for an already-revoked projection but does not trigger a mutation denial, refetch current access, or prove stale controls disappear after invalidation.
- Contract: `tasks.json` T13 requires responsive interaction tests for capability refresh and normalized race-denial feedback; `sad.md` §6.5 step 4 requires a concurrent-revocation denial to refetch current access, remove stale controls, and present the normalized safe explanation. This affects AC-15 and AC-19.
- Required change: add an integrated `AccessWorkspace`/RTK Query test that starts with a permitted mutation, returns a normalized authorization denial, verifies the global error presentation, verifies current-access invalidation/refetch, and proves the stale mutation controls disappear without a successful announcement.
- Disposition: unresolved; fix required before ship.

### F4 — Stage 3: access mutations violate the authoritative RTK Query error-handling flow

- Evidence: `apps/web/src/modules/access/components/access-workspace/AccessWorkspace.tsx:166`, `:169`, `:172`, and `:179` call mutation triggers with `.unwrap()` and allow rejected promises to escape the event workflow.
- System rule: `docs/system/guides/web-error-handling.md` §2 explicitly requires awaiting mutation triggers without `.unwrap()`, branching on the result, and executing success-only state changes only when `data` exists. The same boundary is required by `docs/system/adr/02-08-2026-rtk-query-for-web-api-calls.md` §Decision.
- Required change: return/handle RTK Query mutation results explicitly and prevent success announcements or dialog closure on errors; retain centralized error-toast handling.
- Disposition: unresolved; fix required before ship.

### F5 — Stage 3: completed access mutations omit required success toasts

- Evidence: `apps/web/src/modules/access/components/access-administration/AccessAdministration.tsx:178`, `:192`, `:205`, and `:230` only update an ARIA live-region announcement and close the dialog after success; no access-owned success-alert adapter or success toast exists under `apps/web/src/modules/access/alerts/`.
- System rule: `docs/system/guides/web-error-handling.md` §4 requires a translated, action-specific success toast after every completed user-triggered action except login, reads, navigation, and local-only changes; §2 assigns feature-owned alerts to `modules/<module>/alerts/`. This also conflicts with AC-03 and AC-08, whose observable outcomes require confirmation.
- Required change: add localized access success-alert adapters and invoke them only after confirmed mutation success; test each supported action and both locales.
- Disposition: unresolved; fix required before ship.

### F6 — Stage 2: access read error and empty states collapse into an empty list

- Evidence: `apps/web/src/modules/access/components/access-workspace/AccessWorkspace.tsx:74-94`, `:106-122`, and `:134-150` distinguish only loading from all other outcomes. A rejected query and a successful empty query both render an unlabelled empty list, with no explicit empty or safe error state.
- Contract: `sad.md` §8 “Web state, freshness, and accessibility” requires explicit loading, empty, partial-authority, denied, validation, success, and rollback-safe error states. `tasks.json` T12 requires the approved responsive workspace behavior for AC-20 through AC-22.
- Required change: render and test distinct localized empty and normalized error states for each authorized dataset without disclosing protected information.
- Disposition: unresolved; fix required before ship.

### F7 — Stage 3: the access REST adapter bypasses the required module structure

- Evidence: `apps/server/src/access/access.module.ts:2-13` registers controllers in a feature-root `AccessModule`; controllers are stored directly under `access/rest/`, and the feature has neither `rest/controllers/`, `rest/rest.module.ts`, nor `access/index.ts`.
- System rule: `docs/system/server-architecture.md` §Source structure and §NestJS modules and exports, plus `docs/system/guides/adding-a-server-module.md` §5, require REST controllers under `rest/controllers/`, a `rest/rest.module.ts` importing the use-case module, and a feature barrel exporting the runtime module.
- Required change: move the controllers into the prescribed directory, introduce `AccessRestModule`, export it through `access/index.ts`, and wire that runtime module from the application composition root.
- Disposition: unresolved; fix required before ship.

### F8 — Stage 1: Role-name UI does not implement the shared validation contract

- Evidence: `apps/web/src/modules/access/components/access-administration/AccessAdministration.tsx:277` marks the Role-name input only as required; it does not enforce or explain the trimmed-empty, 100-user-perceived-character, or control/format-character rules, and no server field failure is associated with the control.
- Contract: AC-06b requires the violated rule to be explained. `docs/system/frontend-architecture.md` §Components and §Validation and server contracts require shared request-schema reuse and HeroUI-native inline validation.
- Required change: drive the editor with the shared Zod contract and map stable server validation failures to localized HeroUI field errors; add component coverage for each named rule.
- Disposition: unresolved; fix required before ship.
