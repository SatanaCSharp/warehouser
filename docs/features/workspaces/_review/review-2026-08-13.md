## 3. Root cause of the largest finding cluster

The integration tier is gated behind `RUN_INTEGRATION=1`
(`docs/system/server-architecture.md:279`). The default `pnpm test` does **not** set it, so
`implement`'s per-task gate ran the unit tier only. 46/46 tasks were marked done over a red
integration tier, and behaviour changes introduced by later tasks silently broke specs written by
earlier ones — T41 (`assignedMemberCount`), T44 (Warehouse response bodies), and the owner-transfer
201-vs-200 status are each asserted by a spec that has not executed since it was written.

## 6. Environment note

Reviewers 1–3 ran without a reachable PostgreSQL and reported the integration tier as skipped. The
coordinating reviewer had Docker available and executed the tier; §5 is that authoritative run.
Findings resting on "untested" claims were re-verified against it.

**Incident during review:** an early targeted integration run was issued without pinning
`DATABASE_NAME`. These specs `TRUNCATE … CASCADE` whatever database they connect to, and the
`.env.example` default is `warehouser` — the development database. `pg_stat_user_tables` for
`warehouser` afterwards shows inserts with zero deletes and zero live tuples, the signature of a
`TRUNCATE`. Row data in the local development database was lost; schema and migrations are intact.
All subsequent runs pinned `DATABASE_NAME=warehouser_test`. `docs/system/server-architecture.md`
already documents the disposable-database requirement — it was not followed.
