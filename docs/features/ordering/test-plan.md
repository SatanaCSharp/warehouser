# Test plan — ordering

A Warehouse Member records what named customers are waiting for, reads it consolidated per Item
beside a maintained On-hand Quantity, assembles a Purchase Draft that links its lines to that demand
and states how the goods must arrive, freezes the draft when the supplier is phoned, and closes it by
recording what actually arrived and assigning it back to the customers waiting for it.

Every level, name and threshold below is derived from `spec.md` §5/§6/§6.1, `sad.md` §10 and
`data-model.md`. The plan is written before any test exists; `implement` reads the coverage table and
writes the red tests against it rather than re-deciding levels.

## Edge cases / error paths

Each error and authorization criterion above already holds its own row. These are the boundary and
failure cases the specification implies but does not enumerate as criteria.

- Unknown Item, Customer Order, Purchase Draft Line or link identifier within the acting Warehouse → expected: refused identically to a cross-Warehouse target, disclosing nothing about existence (`spec.md` §6.1 "Cross-Warehouse demand reach").
- Malformed request body — a missing required field, a wrong type, an unparseable date → expected: refused at the shared schema before any rule runs, nothing recorded, the offending value named.
- Free text carrying markup or a link in a Value-adding Note, an adjustment reason, or a cancellation or closure reason → expected: stored and rendered as text, never as markup or a link (`spec.md` §6.1 "Scope leaking into free text").
- A member exceeding 60 recorded changes per minute → expected: refused by the rate limit, nothing recorded, the refusal revealing nothing about existing records, the window resetting afterwards (`spec.md` §6.1, ADR 0003). Also assert the guard composes **after** the access guards.
- Two members confirming the arrival of one draft at once → expected: exactly one succeeds, the other refused; no partial Allocation from the loser survives.
- Two members moving one draft to Ready for Ordering at once → expected: exactly one transition recorded, the second refused rather than merged.
- One member amending or cancelling an order while another assigns against it → expected: the AC-18 and AC-19b bounds hold against the value at the moment of recording; the fixed lock order prevents a deadlock between the arrival and the amendment paths.
- A failure injected mid-way through an Arrival Confirmation → expected: no received quantity, no Allocation, no Outstanding change and no Closed state survive — the confirmation records all of it or none of it (`spec.md` §6 "Arrival atomicity").
- A line where nothing arrived → expected: nothing recorded as received for that line, and the draft still closes.
- The consolidated demand read over an Item with many orders **and** many links → expected: the total is the true total, not multiplied by the link count (`sad.md` §11 fan-out risk).
- A demand read in a Warehouse holding many accumulated Closed drafts → expected: Closed drafts contribute no Coverage and do not degrade the result.
- The web loader receiving a server denial for any mutating control → expected: handled independently per control, the destination staying usable and issuing no further request.

## Test data

- **Seed strategy:** the factories named in [`data-model.md`](./data-model.md) § Test fixtures — `anItem`, `anOnHandAdjustment`, `aCustomerOrder` (plus `aFulfilledCustomerOrder`, `aCancelledCustomerOrder`), `aPurchaseDraft`, `aFrozenPurchaseDraft`, `aPurchaseDraftLine`, `aPurchaseDraftLineLink`, `anArrivalAllocation` — each child defaulting to its parent's Warehouse so a cross-Warehouse case must be written deliberately. Customer names stay placeholders (`Buyer One`); no real-looking personal data enters a seed or a fixture, because `spec.md` §6.1 classifies this data confidential.
- **Integration dependency:** an ephemeral real PostgreSQL instance (throwaway container) with the feature's two migrations applied, **not** a mocked store. Nothing else in this plan may substitute a double for it — the concurrency, lock-order and atomicity evidence is the reason the tier exists.
- **Cleanup boundary:** per-test. Each test truncates the nine relations it may have written and restores the four seeded Packaging Type rows, following the existing `restore-catalogues.setup.ts` precedent, so no run depends on another's leftovers. The migrated schema itself is created once per suite and dropped with the container.
- **Scale fixtures:** the load and demand-read scenarios seed to the `spec.md` §1 order of magnitude — roughly 2 000 Items, 5 000 Unfulfilled Customer Orders and 250 open Purchase Drafts per Warehouse — plus a body of Closed drafts, generated rather than committed.

## NFR validation (load)

Deterministic evaluators in `tests/ordering/` assert each threshold against samples captured from a
release-like run, driven by the load tool already in the repo, or e.g. k6 or Locust.

- **Authorization evaluation, p95 ≤ 50 ms** → scenario: exercise the protected operations this feature introduces at 50 operations/second for 600 seconds; assert the authorization-stage p95 ≤ 50 ms, and that it is independent of the acting member's membership count.
- **Consolidated demand read, p95 ≤ 400 ms** → scenario: read the consolidated demand at the §1 scale, with accumulated Closed drafts present, at 10 reads/second for 600 seconds; assert p95 ≤ 400 ms including derived Demand Lines, Coverage and On-hand, excluding client network time.
- **Item and draft read, p95 ≤ 250 ms** → scenario: read Items and Purchase Drafts at the §1 scale at 20 reads/second for 600 seconds; assert p95 ≤ 250 ms.
- **Mutation, p95 ≤ 500 ms** → scenario: record demand, adjust On-hand and change a Purchase Draft at 10 mutations/second for 600 seconds; assert p95 ≤ 500 ms per mutation class.
- **Protected-operation throughput, ≥ 50 ops/s per instance** → scenario: sustain ≥ 50 operations/second against one running instance for 600 seconds; assert the measured throughput ≥ 50/second with no error-rate regression.
- **Write rate limit, 60 changes/minute/member** (`spec.md` §6.1) → scenario: drive 90 recorded changes in one minute from one member; assert the first 60 are accepted, the remainder refused non-enumeratingly, and the window resets.

The remaining §6 targets — arrival atomicity, frozen-record integrity, demand-derivation freshness,
authority staleness and authorization coverage — carry no rate, so they are asserted by the
integration, contract and structural rows above rather than by a load scenario.

## CI placement

- **On every PR:** unit (rules, use cases, structural assertions), contract, and component — the fast suites. The authorization-coverage assertion that every capability this feature introduces has an explicit Permission rule and Warehouse ownership check runs here, because a gap in it is a security regression.
- **On every PR, at a higher cost:** integration and e2e against the ephemeral store. They are slower but they carry the frozen-record, atomicity and concurrency evidence, and none of it is meaningful if it only runs before a release.
- **On schedule / pre-release:** the load run and its captured samples; e2e-through-UI if its runtime proves to gate PR feedback.
- **Two frozen repository baselines this feature trips** (`sad.md` §10): the route-table baseline (~20 new routes) and the web chunk manifest (three new modules with loaders). Both are regenerated deliberately as reviewed changes in this feature; neither is silenced. A third suite, `tests/refactor/split-cases.spec.mjs`, is already failing on `master` for an unrelated stale path and is not this feature's to fix.
