# Test plan — delivery-addresses

A Warehouse maintains its Customers and their Delivery Addresses as records it owns, states where
each Customer Order's goods are going, sets each Purchase Draft Line to travel Via Warehouse or
Direct to Customer, freezes both with the line at Ready for Ordering, reports Address Drift when the
demand behind a frozen line is redirected, and records an ending per line rather than one per draft.
Customer identity becomes readable only under `CUSTOMERS:WATCH` — on the fifteen surfaces that
already ship it as well as the ones this feature adds.

Every level, name and threshold below is derived from `spec.md` §5/§6/§6.1, `sad.md` §10/§11 and
`data-model.md`. The plan is written before any test exists; `implement` reads the coverage table and
writes the red tests against it rather than re-deciding levels.

## Edge cases / error paths

Each error and authorization criterion above already holds its own dedicated row. These are the
boundary and failure cases the specification and the design imply but do not enumerate as criteria.

- Unknown Customer, Delivery Address, Purchase Draft Line or link identifier within the acting Warehouse → expected: refused identically to a cross-Warehouse target, disclosing nothing about existence (`spec.md` §6.1 "Cross-Warehouse customer reach").
- Malformed request body — a missing required field, a wrong type, an unparseable identifier → expected: refused at the shared schema before any rule runs, nothing recorded, the offending value named.
- Free text carrying markup or a link in a Delivery Address or its access notes → expected: stored and rendered as text, never as markup or a link (`spec.md` §6.1 "Address and access notes as free text").
- A member exceeding the ordering write rate limit while recording Customers and addresses → expected: refused by the limit, nothing recorded, the refusal revealing nothing about existing records, the window resetting; the limiter composes **after** the access guards (`spec.md` §6.1 "Customer and address spam").
- Two members marking a different Delivery Address as Main at once → expected: exactly one succeeds; the partial unique constraint is the arbiter and the loser maps to a stable concurrency refusal, never a silent no-op.
- A redirection racing a freeze on a draft linked to that order → expected: the frozen link snapshot holds either the pre- or the post-redirect address and never a mix; drift is reported or not on the next read accordingly.
- Two members recording an ending on one line at once → expected: exactly one recorded; the loser's conditional update affects zero rows and returns a typed concurrency refusal.
- Two members recording the last two outstanding endings at once → expected: the draft moves to Closed exactly once.
- A failure injected mid-way through one line's ending → expected: no recorded quantity, no Allocation, no Outstanding change and no Closed state survives — one line's ending is written whole or not at all (`spec.md` §6 "Ending atomicity").
- A line where nothing arrived, or nothing was delivered → expected: the ending is recorded with nothing assigned, and it still counts as that line's ending for the closure predicate.
- A Customer Order going to an address that is afterwards deactivated → expected: the order keeps naming it and keeps counting (AC-06a); the address stops being offered by every picker after the deactivation invalidates their tags.
- The Warehouse's own Delivery Address corrected after lines were frozen against it → expected: every frozen value unchanged, and no drift arises from it, because Address Drift is defined against the demand's address (AC-18).
- A linked Customer Order cancelled or amended after the freeze → expected: this feature's frozen delivery values are untouched and report no address drift; `ordering`'s quantity-and-state drift continues to behave exactly as before.
- A frozen draft closed with a reason while some lines still have no ending → expected: the draft closes whatever remains unrecorded, and the whole-draft closure stays available at any time (`spec.md` §8 6th, [ADR 0002](./adr/0002-per-line-purchase-draft-endings.md)).
- A Warehouse that has never had its own Delivery Address recorded → expected: the default state of the seed, from which every Via Warehouse freeze is refused (AC-16a) until it is recorded.
- The web loader receiving a server denial for any mutating control → expected: handled independently per control, the destination staying usable and issuing no further request.
- Every new translation key present in both locales → expected: en/uk parity, and the locale baseline regenerated deliberately in the existing key order rather than re-sorted (`sad.md` §10 gate 2).

## Test data

- **Seed strategy:** the factories named in [`data-model.md`](./data-model.md) § Test fixtures — `aCustomer` / `anInactiveCustomer`, `aCustomerDeliveryAddress` / `aMainDeliveryAddress` / `anInactiveDeliveryAddress`, `aCustomerOrderNamingACustomer` **and** `aTypedNameCustomerOrder` as first-class shapes so AC-24's distinction is tested in both directions, `aViaWarehouseLine` / `aDirectToCustomerLine` / `aFrozenLine`, and `aWarehouseWithDeliveryAddress` beside the default `aWarehouse` that deliberately keeps **no** address. Each child defaults to its parent's Warehouse, so a cross-Warehouse case must be written deliberately.
- **No real-looking personal data in any seed or fixture.** Customer names, address text and access notes stay obvious placeholders (`Buyer One`, `Dock A, Placeholder Road`, `Gate code: 0000`), because `spec.md` §6.1 classifies this data confidential and treats an access note as the means of physical access.
- **Integration dependency:** an ephemeral real PostgreSQL-compatible store spun up per suite with the feature's three staged migrations applied, torn down after — **not** a mocked store. Its single documented limit is stated rather than hidden: one backend, so the lock order and the conditional-update races are asserted by statement shape and zero-row behaviour and the true races stay unproven (`sad.md` §11). No row in this plan may claim more than that.
- **Cleanup boundary:** per-test. Each test truncates the two new relations and the rows it wrote in the four changed ones, and restores the Permission catalogue and grant rows the third migration inserts, following the existing catalogue-restore setup precedent. The migrated schema is created once per suite and discarded with the store.
- **Scale fixtures:** the read scenarios seed to the `spec.md` §1 order of magnitude — roughly 500 Customers and 1 500 Delivery Addresses per Warehouse on top of `ordering`'s ~2 000 Items, ~5 000 Unfulfilled Customer Orders and ~250 open Purchase Drafts — plus a body of Closed drafts. Generated, never committed.
- **Web fixtures:** both the redacted and the unredacted form of every identity-bearing projection is a fixture, so a component test can assert the withheld case without a server. The Warehouse Delivery Address is fixtured **unredacted** for a member without `CUSTOMERS:WATCH`, because it is the operator's own premises data.
- **Migrations are not verified by tests.** They are applied **and reverted** against the real development database with rows present, including the Via Warehouse backfill against pre-existing draft lines (`sad.md` §10, `data-model.md` § Safe evolution).

## NFR validation (load)

**Every scenario below is `Blocked`.** `spec.md` §6 carries five numeric targets, and `sad.md` §11
records that the real-PostgreSQL tier and its load smokes were removed by decision, with the standing
instruction: _"Do not add specs that would pass for the wrong reason, and do not report the target as
met."_ Each target is therefore written out in full so it stays traceable and runnable the moment a
real-PostgreSQL tier is reintroduced — and none of them is implemented, run, or reported as met in
this feature. The tool stays the one already in the repo, or e.g. k6 or Locust.

## CI placement

- **On every PR:** unit — the domain rules, the use cases against doubles, the six redaction projections, the guard behaviour, and the structural checks — plus contract and component. The architecture check that every identity-bearing read declares the observed Permission runs here, because a gap in it is a security regression and `sad.md` §11 makes it one of only two mechanical defences for the fifteen-surface retrofit.
- **On every PR, at a higher cost:** integration and e2e against the ephemeral store. They carry the freeze, capture-by-value, drift and per-line ending evidence, none of which is meaningful if it only runs before a release.
- **On schedule / pre-release:** e2e-through-UI if its runtime proves to gate PR feedback. The load run stays out of CI entirely while it is Blocked.
- **Not in CI:** the migration apply-and-revert against the populated development database, and the security review `spec.md` §6.1 requires — both are release gates.
- **Four repository gates this feature trips** (`sad.md` §10), each reconciled deliberately in the same change and never silenced: the route-table baseline (~15 added routes and one withdrawn), the locale-key baseline (regenerated in existing key order), the two `apps/web` aliases each new contracts subpath needs — with `pnpm --filter @warehouser/web build` part of the definition of done, because a missing alias breaks **only** the build while every suite stays green — and the absence of any `apps/web` integration script, which makes the web half's integration verdict _non-red_ rather than green.
