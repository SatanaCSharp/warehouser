### C. Concurrency correctness

18. **[stage-1, escalated] Two concurrent last endings leave the draft permanently in
    `ready_for_ordering`** —
    `apps/server/src/shared/domain/repositories/arrival-confirmation.repository.ts`:236-256;
    AC: AC-19; problem: `lockDraftLineForEnding` takes no row lock by design (:141, "this takes no
    explicit row lock"), contradicting `sad.md` §6.10 step 2 ("resolves the draft in
    `ready_for_ordering` **under lock**"), and `@Transactional()` defaults to READ COMMITTED
    (`shared/database/db-transaction.service.ts`:26). Two members ending the last two lines
    concurrently update disjoint line rows, so nothing serialises them; each closure
    `UPDATE … NOT EXISTS (… ending_recorded_at IS NULL)` evaluates its subquery against a snapshot in
    which the _other_ line is still un-ended, so **both** affect zero rows. Every line then carries an
    ending and the draft never reaches Closed — AC-19's observable outcome fails. The design comment
    reasoned about "cannot both close it" and did not consider "neither closes it".

    _Escalated from the reviewer's stage-2 to stage-1 by the coordinating pass:_ AC-19's
    business-observable outcome is not produced under a realistic interleaving, and `sad.md`
    prescribed the lock that prevents it.

    _Reviewer overstatement corrected:_ the report called the state unrepairable. It is not —
    `close-purchase-draft.command.ts`:66 gates on `isReadyForOrderingDraft(header.state)` and the
    stuck draft is in that state, so close-with-a-reason succeeds. The defect is that it misrecords a
    normally-completed draft as abandoned.

    Suggested: take `SELECT … FOR UPDATE` on the `purchase_drafts` row in `lockDraftLineForEnding` —
    the lock `sad.md` §6.10 and `data-model.md`'s lock order both already prescribe.
