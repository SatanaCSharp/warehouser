# Change request — modules-level-refactor

## 1. Behavioral delta

When a contributor adds or extends functionality for a domain entity that lives inside a Workspace,
current behavior is that the code lands in the module of the entity that **contains** it — Warehouse
administration and workspace-level Access both live inside `workspace`/`workspaces`, and
`docs/system` records no rule against it; approved behavior will be that code lands in the module of
the entity that **owns** it: every domain entity owns one top-level module (`modules/<entity>` on
web, `src/<entity>` on server), a capability exercised at more than one scope is owned by one module
that carries the views and use cases for every scope, modules never nest, and `docs/system` states
the ownership rule as a convention a reviewer and a test can both check.

### 1.1 Why `change-request` and not `decide-adr`

This request changes no user-observable behavior, which is the condition
[`SKILL.md`](../../../.claude/skills/change-request/SKILL.md) uses to route work to `decide-adr`. It
is filed as a change request anyway, deliberately:

- The deliverable is not the decision. The decision is one document (CH-D4); the request also
  relocates roughly 150 files across two applications, splits four source files, rewrites five
  executable boundary specs and adds a sixth, and re-wires the NestJS module graph. That is
  implementation work with a rollout order, an abort threshold and a rollback, none of which an ADR
  carries.
- The rules being changed are documented system rules with consumers. `adding-a-web-module.md`,
  `adding-a-server-module.md` and `placing-web-components.md` are read before every change by
  contract (`AGENTS.md`), and one of them (CH-D3) currently instructs the opposite of what this
  request approves. Amending a rule that instructs contributors is an override, and it needs the
  old-to-new trace §3 provides.
- The regression surface is the whole product. "Nothing changes" is the claim under test across ~150
  moved files, so it needs acceptance criteria — §5.1 of [`spec.md`](./spec.md#51-regression-boundaries)
  is the substance of this request, and ADRs have no equivalent.

CH-D4 is therefore an ADR **produced by** this request, not a substitute for it.

## 2. Motivation

Warehouse is a domain entity with its own lifecycle, its own membership, and — imminently — its own
subordinate entities. It is not a workspace concern that happens to have a name. Today it has no
home:

- On web, `apps/web/src/modules/warehouse/` is a four-file stub (a dashboard route rendering
  `DesignSystemExample`, plus `useRecordWarehouseEntry`). The actual Warehouse domain — twelve
  administration components, `workspace-warehouses-api.ts`, six hooks, `warehouse-name-form.schema.ts`
  and the largest spec file in the application (`WarehousesTab.spec.tsx`, 1122 lines) — lives under
  `modules/workspace/`.
- On server, there is no `warehouses` module at all. `create`/`rename`/`archive`/`restore`,
  `list-workspace-warehouses`, `WarehouseController` and `warehouse-mutation.dto.ts` live under
  `src/workspaces/`, and four of the nineteen factories in
  `workspaces/domain/errors/workspace.errors.ts` describe Warehouse failures.

Access has the mirror problem. It is one capability — roles, permissions, membership — exercised at
two scopes, and only one scope lives in the access module:

- Web `modules/access/` is warehouse-scoped exclusively (every endpoint built through
  `shared/api/warehouse-path.ts`). A parallel, near-duplicate workspace-scoped implementation lives
  in `modules/workspace/`: `members/`, `roles/` and `permissions/` component trees, three API
  slices, thirteen hooks, and its own `MutationOutcome`, `useFormFieldErrors`, mutation adapter,
  feedback adapter and permission-label hook — each a near-copy of the access module's own.
- Server `src/access/` is warehouse-scoped exclusively. The workspace-scoped copy — workspace role
  CRUD, workspace membership, owner transfer, `workspace-authority.predicates.ts`,
  `workspace-role-deletion.service.ts` — lives in `src/workspaces/`.

The result is a rule nobody wrote down but everybody follows: _whatever a Workspace contains, put it
in the workspace module_. The workspace module is 80 files on web and 79 on server, and it is the
only module growing.

This is needed now because of what comes next. Warehouse is about to own Locations, crates, pallets
and picking. Under the current de-facto rule each of those is a Workspace concern by transitivity
and lands in `workspace`/`workspaces` too, or — more likely — each becomes its own top-level module
while Warehouse itself remains a stub inside the workspace module, which is the same mistake
inverted. Establishing entity ownership now costs one behavior-preserving move of code that already
exists and is already covered by tests. Establishing it after Locations, crates and picking ship
costs the same move plus theirs, against a module nobody wants to touch.

The second half of the request is why the rule is written into `docs/system` rather than only
applied: a layout without a stated rule regresses at the first feature that has nowhere obvious to
go. `AGENTS.md` already makes `docs/system` the instruction set every contributor and agent reads
before implementing; the ownership rule belongs there or it does not exist.

## 2.1 Terms fixed by this request

- **Owning module** — the module named for the domain entity whose invariants the code enforces, not
  the entity that contains it and not the URL prefix it is served under. Warehouse lifecycle is owned
  by `warehouse`/`warehouses` even though a Warehouse belongs to a Workspace; workspace roles are
  owned by `access` even though they are scoped to a Workspace.
- **Scope of a capability** — the entity a capability's rules are evaluated against. Access has two
  scopes today, Warehouse and Workspace. Both are owned by the `access` module; the scope appears in
  the file and symbol names (`WorkspaceRolesTab`, `AssignWorkspaceRoleCommand`), never in a second
  module.
- **Flat modules** — the module list is one level deep. `modules/<entity>/` on web and `src/<entity>/`
  on server contain layer directories (`components/`, `hooks/`, `api/`, `domain/`, `usecases/`,
  `rest/`), never another module. A module that feels like it needs a submodule is a module that
  should be promoted to its own top-level sibling.
- **Composition layer (web)** — `apps/web/src/shared/`, `guards/`, `routes/`, `router.ts`, `store/`
  and `test/`. This is the application assembling itself out of modules. It is **not** a module and
  owns no domain, but the boundary rule **does** bind it: it may import a module only through that
  module's declared public surface. It differs from a module in _what_ it may import — any module's
  surface, where a module may reach only a sibling's — not in whether the rule reaches it. Its files
  nonetheless stay where they are; see §2.2.
- **Public surface of a web module** — an **enumerated per-module export list**, declared as data the
  boundary spec reads. It is a list, not a category, because a category cannot be checked without
  re-deciding per file what counts as "page-level". It contains that module's page-level views (a
  page, a route component, a tab); `modules/auth/store/` (selectors and action creators — identity is
  application-wide, `src/store/index.ts` already registers its reducer globally, and both route guards
  already read `selectIsAuthenticated` from it); and the three targets the composition layer imports
  today — `modules/warehouse/hooks/useRecordWarehouseEntry` (read by `shared/layouts/WarehouseLayout.tsx`),
  `modules/auth/session/session` (read by `guards/auth.guard.ts` and `guards/anonymous-user.guard.ts`)
  and `modules/auth/sign-out/components/SignOutButton` (read by `shared/layouts/RootLayout.tsx`).
  Imports are legal against the declared surface and illegal against anything else.
  **Corrected at `tasks` per sad.md §11 O2:** the real production import graph has **nine**
  composition-layer targets, not the three named above — add every module's `route` (registered by
  `router.ts`), `modules/auth/store/auth.slice` (read by `store/index.ts` and two test fixtures) and
  `modules/auth/store/auth.selectors` (read by both route guards). The enumerated declaration in
  [`sad.md` §5.2](./sad.md#52-web-modules-after-the-move) and
  [ADR 0001](./adr/0001-enumerated-web-module-surface-declaration.md) is authoritative; all nine are
  declared surface, so CH-W5 still passes with an empty exception list.
- **Declared surface entry vs. exception** — a declared entry is the rule's **input**: the rule reads
  the list and permits what it names. An **exception** is an import permitted _despite_ violating the
  rule. This request has zero exceptions, and §6's abort threshold is written against exceptions only
  — an entry appearing in a module's surface declaration never trips it, while an allowlist of
  imports that would otherwise fail always does.
- **Public surface of a server module** — the providers its `usecases/usecase.module.ts` exports, and
  its `index.ts` barrel. `docs/system/server-architecture.md` §"Dependency direction" already states
  that modules "communicate through exported use-case modules, explicit services, or events, not
  through another module's controller or persistence implementation." This request **extends** that
  to error factories, domain predicates and DTOs, which the existing wording does not reach. It is a
  new, stricter clause, not a restatement — CH-S6 owns it and CR-AC-08 tests it.
- **Behavior-preserving** — every HTTP route, status code, request shape, response shape,
  permission, invariant, translated string and rendered screen is identical before and after. Test
  assertions divide in two: a **behavioral** assertion (what the system does) may not change; a
  **structural** assertion (a file path, a module name, an import graph, a handler inventory) may,
  because its subject is exactly what this request moves. §6's abort threshold is written against
  behavioral assertions only, and CH-S6 names every spec whose assertions are structural.

## 2.2 Why the composition layer imports module surfaces

An earlier draft of this request moved `shared/api/warehouse-path.ts`,
`shared/hooks/useEnteredWarehouse.ts`, `guards/warehouse-entry.guard.ts` and
`shared/api/access-permissions-api.ts` into their owning modules, on the reasoning that
single-owner domain code does not belong in `shared/`. Checking the consumers refuted it: those four
files have fourteen consumers outside `modules/` — `shared/hooks/usePermissions.ts`,
`shared/hooks/useEnteredContext.ts`, `shared/layouts/{WarehouseSwitcher,WarehouseLayout}.tsx`,
`shared/components/WarehouseEntryRefusal.tsx`, `routes/warehouse.route.tsx`, `test/render.tsx` and
their specs. Moving them would convert one recorded `shared/` → module exception into roughly
fourteen, and a boundary rule enumerating its own violations is an allowlist, not a rule.

`shared/api/workspace-context-api.ts` makes the same point harder: it has twelve consumers spread
across `guards/`, `routes/`, `shared/`, `test/` and three different modules. There is no module that
owns it.

So the rule is stated where it holds: **nothing reaches into a module except through its declared
surface** — modules into each other, and the composition layer into modules alike. What differs is
reach, not exemption: the composition layer may import any module's surface, a module only a
sibling's. That is also what
[`placing-web-components.md`](../../system/guides/placing-web-components.md) already prescribes
("keep it at the shared ancestor level… `shared/components/` once a second module needs it"). Those
four files stay where they are, and CR-RG-07 records that as a boundary this request does not cross.

Binding the composition layer costs three declarations, not three refactors. Its only imports of
module internals today are `shared/layouts/WarehouseLayout.tsx` → `useRecordWarehouseEntry`,
`guards/auth.guard.ts` → `modules/auth/session/session` and `shared/layouts/RootLayout.tsx` →
`SignOutButton`; each target is declared surface of its module in §2.1, so CH-W5 passes on day one
without an exception list and none of the three files is edited. The alternative — leaving the layer
unconstrained — would mean the rule says nothing about the largest category of imports into modules,
and a boundary spec that scans only `modules/**` cannot tell a legitimate composition import from a
`shared/` file that has quietly absorbed a module's internals.

## 5. Compatibility and transition

- **Compatibility:** **backward-compatible**, deliberately and completely. No HTTP path, status code,
  request shape, response shape, permission, invariant, migration, contract export, translated string
  or rendered screen changes. What changes is where the source lives and what `docs/system` says
  about where source must live. The one new _convention_ — a web route owner may import another
  module's page-level views (CH-W3) — is additive; it legalizes something no code did before rather
  than changing something code did.
- **Deliberate decoupling of source layout from URL layout.** Controllers move module while their
  `@Controller` prefixes stay byte-identical, which means `access` and `warehouses` each own a
  controller mounted under `api/v1/workspace…`. That looks wrong until stated as a rule, so it is
  one: **a module owns behavior, a URL prefix expresses a client-facing resource hierarchy, and the
  two are allowed to disagree.** Renaming URLs in the same change would convert a behavior-preserving
  refactor into a breaking API change, invalidate every web API slice, and make it impossible to tell
  a refactor bug from an intended change when a test fails. If the URL hierarchy should later follow
  the module hierarchy, that is a separate, genuinely breaking change request.
- **The composition layer is not a module.** §2.2 states why `shared/`, `guards/`, `routes/` and
  `test/` may import module surfaces. Without that, the boundary rule this request introduces would
  need roughly fourteen recorded exceptions on day one and would be an allowlist rather than a rule.
- **Affected consumers:** contributors and coding agents only. There is no external API consumer, no
  mobile client, no published package surface change, and no persisted-data reinterpretation.
  `packages/contracts` export subpaths (`./access`, `./auth`, `./users`, `./workspaces`) are
  unchanged, so nothing outside this repository observes the refactor. Within the repository, every
  import specifier naming a moved file is affected — that is the whole cost.
- **Transition window and exit condition:** none, and none is possible. A module move has no
  dual-running state: a file exists at exactly one path, and a half-moved graph does not compile. Old
  and new layouts never coexist. Exit condition is that the change ships whole, per application —
  §6 permits web and server to land as separate commit sets but never permits a single module's move
  to be split across them.
- **Existing-data treatment:** N/A. No data is read, written, migrated or reinterpreted.

## 6. Rollout

No feature flag and no compatibility shim — neither is expressible for a source-layout change.

Order:

1. `clarify` — close §9's open questions. §9.1 and §9.5 decide how large CH-W2 and CH-W3 are; the
   rest default safely.
2. `design` — settle the four things that are decisions rather than moves: the enumerated public
   surface of each web module, which CH-W5's boundary spec reads as data (§9.5); where the duplicate
   access/workspace helpers land (§9.1); the exact per-factory split of `workspace.errors.ts` and the
   `shared/errors/` promotion rule (CH-S2); and the mechanism CR-AC-11 uses to capture the route
   table (§9.6).
3. `plan-tests` — in particular, how CR-RG-01 is _proved_ rather than asserted: a captured route
   table before and after, and a classification of every changed test line as structural or
   behavioral.
4. Write CH-D3 (the `placing-web-components.md` narrowing), CH-D4 (the ADR), the two guide
   extensions **and the one `frontend-architecture.md` sentence CH-D6 pulls forward** — before any
   code moves. Every subsequent move is judged against them; writing them last would mean documenting
   whatever the refactor happened to produce. CH-D3 specifically must precede CH-W3, and the
   `frontend-architecture.md` qualification must precede CH-W1, since it is the document a
   contributor reads before placing the first moved file.
5. Server, one module at a time. **Each commit updates the boundary specs it invalidates**, so every
   commit builds and passes on its own: `warehouses` (CH-S1) → workspace access into `access`
   (CH-S2) → warehouse membership into `access` (CH-S3) → trim `workspaces` (CH-S4) → wiring
   (CH-S5). CH-S6 is not a trailing commit; it is the boundary-spec work distributed across the five,
   plus the two new module boundary specs at the end.
6. Web, one module at a time, same rule: warehouse domain into `modules/warehouse` (CH-W1) →
   workspace access into `modules/access` (CH-W2) → shell composition and multi-consumer residue
   (CH-W3) → i18n namespaces (CH-W4) → the new boundary spec (CH-W5).
7. Index entries (CH-D5).
8. At ship only, reconcile the canonical owners in §8 (CH-D6 and the feature documents).

Monitoring signals: `pnpm --filter @warehouser/server {lint,test,build}`,
`pnpm --filter @warehouser/web {lint,test,build}`, the release-gate suites under `tests/`, and manual
verification of `/workspace`, the warehouse view and the access surface in a browser per the
repository's `run` practice.

**Abort threshold** — release is blocked if any of the following is observed:

- a **behavioral** assertion in an existing test had to change to make the suite pass (a path-valued
  literal, a handler inventory or a file location is structural and is expected to change; an
  expectation about what the system does is not);
- any HTTP route's method, path, guard, permission metadata, DTO or response shape differs from the
  captured baseline (CR-AC-11);
- a boundary spec's _rule_ had to be weakened or deleted rather than re-pathed (CH-S6);
- a `forwardRef()` is needed to resolve the NestJS graph (CR-AC-09);
- a user-visible string changes value rather than namespace (CR-RG-04);
- `access` gains a deep import of `workspaces`, or `users` gains an import of `access`, `auth`,
  `warehouses` or `workspaces` (CR-AC-08);
- the web boundary spec (CH-W5) requires a per-file **exception** list to pass — an import permitted
  despite violating the rule. A module's surface **declaration** is the rule's input and never trips
  this (§2.1); the test is whether the entry would fail the rule if the list were empty.

## 7. Rollback

Pure code revert, per application. The web commits (CH-W1–CH-W5) and the server commits
(CH-S1–CH-S6) are independent of each other and either half can be reverted alone.

Within an application the module commits are **not** independently revertible: reverting CH-S2 while
CH-S4 stands leaves `workspaces` trimmed of code nothing else owns, and the graph does not compile.
Roll back an application by reverting its commits in reverse order, as a set.

No data limitation exists — no migration ran, no persisted value was written or reinterpreted, and
no external consumer observed anything. A revert restores the previous layout exactly.

If ship-time reconciliation (§6 step 8, §8) has already landed, revert that documentation commit too.
The guides, the `placing-web-components.md` narrowing and the ADR (CH-D1–CH-D4) may be left in place
after a code revert **only** if the ADR is marked Superseded and CH-D3's narrowing is reverted with
it; leaving an Accepted ADR describing a layout the repository does not have is worse than having no
ADR.

## 9. Open questions

- [ ] **§9.1 — Where do the duplicated access/workspace helpers land?** CH-W2 brings
      `modules/workspace`'s `workspace-mutation.ts`, `workspace-feedback.ts` and
      `useWorkspacePermissionLabel.ts` into `modules/access`, which already has a near-identical copy
      of each; CH-W3 additionally has to place `useFormFieldErrors.ts`, `useReturnFocusOnClose.ts`
      and `MutationOutcome`, all of which have warehouse-domain **and** access-domain consumers
      today. Default now: the three genuinely generic ones (`useFormFieldErrors`,
      `useReturnFocusOnClose`, `MutationOutcome`) move to `shared/` per
      `placing-web-components.md`'s existing ancestor rule; the three domain-flavoured ones stay as
      two scope-named files each inside `modules/access`, because their copy, error codes and toast
      intent differ by scope and merging them would be a behavior change hiding inside a move.
      **Unresolved sub-question:** `modules/access` already has its own near-copies of
      `useFormFieldErrors.ts`, `useReturnFocusOnClose` and `MutationOutcome`, and no CH row targets
      them — CH-W2/CH-W3 target `modules/workspace/**` only. Consolidating them onto the `shared/`
      version is a merge carrying the same behavior risk this question rejects for the
      domain-flavoured three; leaving both contradicts [`spec.md` §7](./spec.md#7-metrics--kpis)'s
      "1 implementation per capability". The disposition must be decided, not inherited from the move.
      — owner: Tech Lead, due: `design`
- [ ] **§9.2 — Does `src/users/` fold into `access`?** `users` is warehouse-scoped member lifecycle
      mounted at `api/v1/warehouses/:warehouseId/users` — arguably Access management under a different
      name. Default now: no, leave it. It was not requested, it has a deliberate shipped boundary
      (`users/module-boundaries.spec.ts`), and folding it in would triple this request's server
      surface. — owner: Tech Lead, due: `design`
- [ ] **§9.3 — Singular or plural module names?** Web uses `modules/workspace`, `modules/warehouse`,
      `modules/access`; server uses `src/workspaces`, `src/users`, `src/access` and gains
      `src/warehouses`. Default now: leave both conventions — each is internally consistent, and
      renaming for symmetry adds churn to an already large diff for no navigational gain. If decided,
      it belongs in the ADR (CH-D4) as a stated convention. — owner: Tech Lead, due: `design`
- [ ] **§9.4 — Do `packages/contracts` subpaths follow the modules?** Warehouse schemas live under
      `@warehouser/contracts/workspaces`. Default now: unchanged and out of scope. A contracts subpath
      is a published export consumed by both applications; moving it is a separate breaking change and
      would violate CR-RG-03. — owner: Tech Lead, due: `design`
- [ ] **§9.5 — What exactly is each web module's declared public surface, including the composition
      layer's permitted targets?** CH-W5's boundary spec reads an enumerated per-module export list,
      not a category, and CR-AC-04 now binds the composition layer to the same rule — so the list must
      cover both what a sibling module may reach and what `shared/`, `guards/`, `routes/` and `test/`
      may reach. Default now: each module declares its page-level views, plus `modules/auth/store/`,
      plus the three entries the composition layer already imports
      (`modules/warehouse/hooks/useRecordWarehouseEntry`, `modules/auth/session/session`,
      `modules/auth/sign-out/components/SignOutButton`). **Settled, no longer part of this question:**
      `workspace-users-api.ts` goes to `shared/api/` — it is read by workspace-member add _and_ by
      three warehouse-domain consumers (`workspace-warehouses-api.ts:8`,
      `GiveWarehouseAccessDialog.tsx:5`, `WarehousesTab.tsx:7`), so placing it in `access` would create
      exactly the `modules/warehouse` → `modules/access` API-slice imports CR-AC-04 forbids. CH-W2's
      target list is corrected accordingly. — owner: Tech Lead, due: `design`
