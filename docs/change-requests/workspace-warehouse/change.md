# Change request — workspace-warehouse

## 1. Behavioral delta

When an authenticated user works in Warehouser, current behavior is one undifferentiated
authenticated surface — a single sidebar listing Dashboard, Access and Workspace side by side, flat
routes (`/`, `/access`, `/workspace`), and every Warehouse-scoped screen silently resolving its
Warehouse from the stored `effectiveWarehouseId`; approved behavior will be two separate contexts —
a Workspace view at `/workspace` and a Warehouse view entered explicitly and addressed by
`/warehouses/:warehouseId/…` — chosen through one grouped switcher in the top navigation that lists
the Workspace above the Warehouses the actor may enter, with the Workspace row rendered but inert
for an actor holding no Workspace administration authority.

## 2. Motivation

The Workspace boundary shipped (`df929ca`), but the web surface never separated along it. Today the
sidebar mixes both authority levels in one flat list, so a Warehouse Member who is not a Workspace
Member sees a surface shaped by the same navigation as a Workspace Owner, minus omitted entries;
and the Warehouse a screen operates on is invisible — it is read from a stored selection
(`useCurrentPermissions` → `context.effectiveWarehouseId`), so `/access` means a different Warehouse
for the same URL depending on state the user cannot see, cannot link to, and cannot hold two of at
once.

This is needed now because the Warehouse level is about to receive stock, Locations and movement
history. Every one of those features would attach to a Warehouse view that does not yet exist as an
addressable thing, and each would independently re-derive "which Warehouse am I in" from a stored
selection. Establishing the Warehouse view as a URL-addressed context now costs one routing change;
establishing it after stock screens exist costs a migration of every one of them.

Requested and confirmed with the product owner (2026-08-13). Four intake decisions were taken and
are load-bearing for every row below: (1) entering a Warehouse is a context switch inside the
existing session, never a second authentication; (2) the entered Warehouse is carried in the URL;
(3) landing after sign-in resolves by actor, and never chooses between several memberships;
(4) entering a Warehouse requires a membership in it — Workspace authority administers a Warehouse
record, it never opens the Warehouse.

## 2.1 Terms fixed by this request

- **Workspace administration authority** — holding at least one of
  `workspaceAdministrationPermissionIds` (`WAREHOUSES:WATCH`, `WORKSPACE_ROLES:WATCH`,
  `WORKSPACE_MEMBERS:WATCH`, `WORKSPACE:RENAME`), the set already defined in
  `apps/web/src/shared/hooks/useWorkspacePermissions.ts` and already shared by the sidebar's
  Workspace entry and the `/workspace` route guard. This request adds the switcher's Workspace row
  and the landing resolver to that same set. It is deliberately **not** "holds any Workspace
  Permission": a Workspace Member holding only, say, `WORKSPACE_MEMBERS:ADD` cannot open
  `/workspace` today, so treating them as workspace-landing would bounce them between `/` and
  `/workspace` forever. The existing code comment on that constant already states the rule this
  request obeys — it is "the single set the navigation entry, the route guard and the destination's
  own contents must agree on".
- **Entering a Warehouse** — arriving at a `/warehouses/:warehouseId/…` address that the actor is
  permitted to open, by any path: a switcher row, the warehouses tab's Enter action, a typed or
  pasted address, or a restored browser session. It is never an authentication event.
- **Effective Warehouse** — the existing `effectiveWarehouseId` field of `GET /workspace/context`.
  It is already a _derived_ value, not the raw stored column: `ReadWorkspaceContextQuery` returns
  the stored `users.active_warehouse_id` while it names a live non-archived membership, otherwise
  the sole live membership when exactly one exists, otherwise `null`. AC-03b's refusal to choose
  between several memberships is therefore enforced server-side and this request inherits it
  unchanged (CR-RG-04).

## 5. Compatibility and transition

- **Compatibility:** **breaking**, in four respects. (1) Every authenticated address changes —
  `/access` ceases to resolve and `/` stops rendering a dashboard. (2) The approved `workspaces`
  acceptance criteria AC-03 and AC-30 are amended (CH-02, CH-05). (3) `web-shell-navigation`
  CR-AC-02's sidebar contents are superseded (CH-07). (4) The approved `design-ui` frames drawing
  the flat switcher and the mixed sidebar are superseded (CH-09). Nothing at the data or wire level
  breaks: no migration, no contract change, no authorization-rule change.
- **Affected consumers:** authenticated web users only. There is no external API consumer of the web
  addresses, no mobile client, and no server change, so nothing outside the browser is affected. A
  user's stored bookmarks and any in-flight links to `/access` are the concrete breakage.
- **Transition window and exit condition:** none — no dual-running period. Old and new addresses
  never coexist: the flat routes are removed in the same change that introduces the scoped ones.
  Exit condition is that the change ships whole. Deliberately **no** `/access` →
  `/warehouses/:id/access` shim is added, because such a shim could only pick the target Warehouse
  from the effective selection — reintroducing exactly the implicit resolution CH-04 removes, in the
  one code path least likely to be re-examined later. Instead CH-10 adds not-found handling, which
  performs no Warehouse resolution of its own and hands off to the single sanctioned resolver.
- **Existing-data treatment:** no data is reinterpreted in a way that could be wrong. Every stored
  `users.active_warehouse_id` remains valid under CH-05's narrowed use, and a stored value naming a
  Warehouse the member no longer holds a live membership in is already handled by the server's
  existing derivation (§2.1) — it yields the sole live membership or `null`, and the switcher's
  retained "selection ended" message still explains it (CR-RG-03).

## 6. Rollout

Single release, no feature flag — repository convention favors a direct change over a compatibility
shim, and §5 explains why a route shim specifically is undesirable here.

Order: (1) `clarify` — close §9's archived-entry question, which decides CR-AC-17 and CR-RG-02;
(2) `design` — settle the route shape, where the landing resolver lives, and how
`useCurrentPermissions` reads the route parameter without every consumer taking a new argument;
(3) `design-ui` — add the grouped-switcher, context-sidebar and no-context frames to
`docs/mockups/app.pen` and get them approved (this versions the shared design source without yet
flipping which frame `design-handoff.md` declares approved, so it precedes implementation without
editing canonical feature documentation); (4) `plan-tests`; (5) implement the route shape and the
`useCurrentPermissions` change together, since neither is coherent alone; (6) implement the grouped
switcher and the two context sidebars; (7) implement the landing resolver, the not-found handling
and the warehouses-tab Enter action; (8) update every affected web test; (9) at ship time only,
reconcile the five canonical owners in §8.

Monitoring signals: the existing web and server test suites, plus manual verification in a browser
per the repository's `run`/UI-verification practice. No telemetry is added.

Abort threshold: release is blocked if any of the following is observed — a `:warehouseId` the
acting user holds no membership in yields anything other than a refusal (CR-AC-07); a refused entry
re-runs the landing resolver or falls back to another membership; the landing resolver enters a
Warehouse for an actor holding several memberships and no valid stored selection (CR-RG-04); an
actor is bounced between `/` and `/workspace` (§2.1); or any Warehouse-scoped control becomes
reachable outside a Warehouse view.

## 7. Rollback

Pure code revert. Revert the routing, shell, switcher, guard, `usePermissions`, not-found and
warehouses-tab commits together — they are not independently revertible, because the scoped
addresses and the route-parameter permission read are two halves of one behavior (CH-03, CH-04).

No data limitation exists: no migration ran, the server's derivation is untouched, and
`users.active_warehouse_id` values written under the narrowed use are indistinguishable from values
written under the old one, so a revert resumes reading them as "what the member is shown" with no
repair step and no loss.

If ship-time reconciliation (§6 step 9, §8) has already landed, revert that documentation commit
too, so `workspaces/spec.md` and `web-shell-navigation/spec.md` again state their criteria as the
running code implements them. Frames added to `app.pen` may be left unreferenced; that has no
runtime effect.
